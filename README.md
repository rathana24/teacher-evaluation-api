# Teacher Evaluation Backend

Backend for the school's teaching-evaluation workflow, built with NestJS, TypeScript, Prisma and PostgreSQL. Administrators prepare academic structure, students, teaching assignments and questionnaires; students save drafts and submit responses stored separately from identifiable completion tracking; lecturers receive their own results after evaluations are CLOSED. Lecturer reports omit direct student identifiers; small-cohort and identifying-text risks remain subject to school policy.

Use the [consolidated Markdown report](docs/BACKEND_PROJECT_REPORT.md) or its synchronized [Word report](docs/BACKEND_PROJECT_REPORT.docx) for professor review, thesis writing and defense preparation. [TESTING.md](TESTING.md) contains the isolated setup and verification procedure. These four documents are the maintained documentation set; `docs/` contains exactly the two report formats.

## Complete school workflow

For a new empty installation, provision the first administrator through the secure CLI below, then sign in. ADMIN remains school-wide; a primary department is profile metadata.

1. Create departments and majors. Use POST /api/academic-years/setup with its UUID v4 Idempotency-Key to create a year and Semester 1/2 atomically; /:id/complete-setup fills only missing semesters. Separate year/semester CRUD remains available. No automatic student-group or teaching rollover is implemented.
2. Add lecturers, students and generations; approve the student's yearly placement/group.
3. Approve curriculum rules/revisions. New assignments require a valid student year and applicable approval in the selected semester year.
4. Use /api/course-offerings/create-with-enrollments/preview and /confirm to review explicit rosters and atomically create assignments/scopes/enrollments. Keep its review ID/body for retries/recovery. Existing standalone assignment/enrollment routes remain separate operations.
5. Create a named question set and usable questionnaire version.
6. Review evaluation assignment, questionnaire, schedule and participant selection; confirm the stored review.
7. Open a valid evaluation, deliberately retaining an assigned older version through its reviewed workflow when needed.
8. Students access the effective questionnaire, save/resume a draft and submit once.
9. Apply newer questions only through the reviewed unfinished-participant workflow, preserving protected drafts and completed answers.
10. An ADMIN may extend an active OPEN evaluation with an end_at-only, strictly later deadline. Close the evaluation to release owned lecturer results/comments; administrators monitor participation and reports. Upcoming, expired and CLOSED evaluations cannot be extended.

Approved rules require an ACTIVE student account and an explicit group for the relevant year. REPEAT/TRANSFER progression follows the last approved placement. PAUSE persists until RESUME. Placement/group changes do not rewrite frozen evaluation membership or anonymous history.

The student self-profile now includes student.academic_context from the shared academic resolver: the selected year, its actual placement/group/major, effective year and progression, and placement_eligible as true/false or null when unavailable. A missing current-year group is never filled from older records. Offering lists/details expose persisted _count.enrollments, including zero; this does not certify evaluation eligibility. Backend field availability does not establish frontend consumption or browser acceptance.

## Database integrity and identifiers

Account `users.id` and profile `students.id` are different. Student CRUD/placement uses profile IDs; enrollment/participant confirmation uses account IDs. Responses serialize BigInt IDs as strings; follow each DTO because some department/course/semester inputs remain numbers.

Final response rows contain no student or participant ID. Completion is stored separately on participants. Questionnaire versions preserve answer meaning; curriculum bindings and historical target labels preserve the context used at confirmation. Lecturer results require CLOSED evaluations.

SQL-owned safeguards include at most one active academic year, one primary department while retaining secondary memberships, global literal question-set title uniqueness, nullable offering uniqueness, bounded student years and ordered dates. The supplied migrations preserve these constraints; a schema file alone is not the whole database contract.

Normal school records and synthetic testing belong in separate databases. Only the guarded local `teacher_evaluation_test` connection is used for automated/synthetic evaluation. Official recovery and another school deployment require their own reviewed evidence and authorization.


The second command prompts for name/email and a hidden password twice. Existing environment values take precedence over the chosen env file; the CLI displays database/schema names before input, without connection credentials. The command refuses any existing ADMIN (including inactive), other account or school data. It permits the unchanged AMS department inserted by an existing migration, and preserves it exactly. Existing accounts must be managed through authorized administration/recovery procedures, not by rerunning bootstrap.

Passwords follow the existing bcrypt cost 10 and 6-character/72-UTF-8-byte limits, with blank passwords rejected. Do not put credentials in command arguments/history or commit them. Automated operators may use --stdin with one bounded UTF-8 JSON object containing full_name, email and password delivered by a secure secret-management pipe; there are no default credentials, password environment flags or secret-file examples.
